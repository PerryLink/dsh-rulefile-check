## 二、§0.3 + R26：**peer 区间 —— 这是最容易装不上的根因**

报告用 checkout 里实际的 `semver@7.8.5` 复现了一个矩阵，结论是
**推荐写法只有 `>=0.2.0-0 <0.3.0`**，而 `^0.2.0`／`~0.2.0`／`>=0.2.0` 会**把活宿主拒之门外**。

**本仓库实际声明的区间（53 个插件完全一致）**：

```text
@deepseek-ai/dsh-tools   >=0.1.2-rc.1 <0.2.0 || >=0.2.0-0 <0.3.0
@deepseek-ai/cordis      ^4.0.2
@deepseek-ai/schemastery ^3.18.2
```

**我用同一份 semver 实测**（`includePrerelease: true`）：

| 版本 | 本仓库区间 | 对照：`^0.2.0` |
|---|---|---|
| `0.2.0-rc.2`（报告所指活宿主） | ✅ **ACCEPTED** | ❌ **REJECTED** |
| `0.2.1-alpha.1`（本机 CLI） | ✅ ACCEPTED | ✅ ok |
| `0.1.2-rc.1` | ✅ ACCEPTED | — |
| `0.3.0` | ❌ REJECTED（正确：跨大版本） | — |
| `0.1.1` | ❌ REJECTED（正确：低于下限） | — |

⇒ ✅ **本仓库的区间同时接受报告所指的活宿主与本机 CLI，且正确拒绝越界版本。**
**并且我复现了报告的核心警告**：`^0.2.0`／`~0.2.0`／`>=0.2.0` 三种写法**都拒绝 `0.2.0-rc.2`**。
⚠️ **这解释了为什么"我自己机器上能跑"没有验证价值** —— 本机是 alpha，而活宿主可能是 rc。

**另一条（R26 末句）**：`peerDependencies` 里任何**非字符串** range 会让门禁抛错并转为拒绝。
本仓库全部为字符串（审计确认）。

## 四、唯一的真实发现：**R56 —— `engines.dsh` 是"假保险"**

**53/53 个插件都声明了 `engines.dsh`。**

报告对此的定性（第 178 行）值得逐字引用：

> `engines.dsh` 虚假保险是**测得最普遍**的缺陷（81–100%），**但它本身不伤害任何东西** ——
> 它只是**拿走了作者以为拥有的保护**。

**我的判断：保留它，但不再把它当兼容性保证。**

理由：① 报告明确说它**不伤害任何东西**；② 真正的兼容性声明是 **`peerDependencies`**（R26），
**本仓库的区间已实测通过两个宿主**；③ **删掉它反而会失去一条对未来读者的提示**。
⇒ **正确的处置是在文档里写明它不是保险，而不是删除它。** 本报告即该说明。

## 八、本轮已修的**真实缺口**：`cordis.patch.yml` **从未被任何测试加载过**

报告 §2.3 **R29** 与 §3.4 第 5 条要求：**"用 `dsh --profile <name> --dump-config` 验证自己的 patch 真的落地了"**。

**审计发现本仓库此前只验证了"文件存在且在 `files[]` 里"，从未加载它。**
⇒ 一个**无法解析、指错插件、或用错 row 动词**的 patch **会照样发布**，
而在报告里这属于 **`not-a-bundle`**（Web 插件管理器直接拒装）。

**已新增共享测试**（`_shared/tests/table-plugin-suite.ts` → `plugin contract > ships a bundle patch that parses and points back at this plugin`），
在 53 个插件上各断言四件事：

1. `package.json#dsh.bundle.patch` 恰为 `./cordis.patch.yml`；
2. `cordis.patch.yml` **在 `files[]` 里**（否则装包时不会被带上）；
3. patch 内容含 `- insert:` 行动词；
4. 其中的 **row `id` 恰好一个且等于本插件名**，`name` 也指回本包。

**测试总数：1516 → 1555（+39）**；四道门全绿。

⚠️ **写这条测试时我连错三次，都是同一类"正则判据"错误**（值得记录）：

| 错误 | 症状 | 原因 |
|---|---|---|
| `^\s*id:` 配 `$` 且**漏了 `m` 标志** | `expected [] to equal ['dsh-…']` | 行首/行尾锚点失效 |
| 补 `m` 但仍用 `$` | 同上 | **文件为 CRLF 时 `$` 仍不匹配** |
| 去掉 `$` 但写成 `^[ \t]*id:` | 同上 | **实测该行是 `    - id: …`** —— `- insert:` 下的 row **本身是列表项**，键前有列表标记 `-` |

⇒ **根因是我不看实际文件内容就写正则。** 后来**把 patch 逐行 dump 出来**才一眼看出 `- id:`。
**教训与第 67 轮"审计脚本必须先自证覆盖范围"同源：正则式判据必须先对着真实样本验证一次。**

## 十、第 84 轮：**工具描述重复句 —— 每个回合都在付费**

审计发现 **53 个插件中有 39 个**在 `description` 中**把同一句话写了两遍**：

```ts
        '材料为 JSON 或 YAML；无法执行的检查会列在 skipped 中。' +
        '材料为 JSON 或 YAML；无法执行的检查会列在 skipped 中。',
```

**这不是"文字不整洁"，而是每个回合都向模型重复计费的 token 浪费** ——
报告 §5 明说「**成本是可见的**：每轮 prompt token、工具 schema token……好插件对这些有预算意识」。

**已全部修复（39 → 0）**，并**新增共享断言**
（`plugin contract > states each sentence of the tool description exactly once`），
把描述里按 `。`／`；` 切出的句子做重复检测 —— **使这类缺陷不可能再被引入**。

⚠️ **我在这条修复上连错三次，全部是"不看真实文件就写正则"**：

| 尝试 | 我当时的判断 | 真实原因 |
|---|---|---|
| 1 | 正则写错 | 模式过窄 |
| 2 | 文件是 CRLF，`$` 不匹配 | **实测该文件没有 CRLF** |
| 3 | 仍是 CRLF | ⚠️ **真因：`\s*[+,]?$` 里 `[+,]?` 是可选的，`\s*` 会吃掉 `' +` 的空格，而正则引擎偏好更少重复、不会回溯到让 `+` 匹配** |

⇒ **改法**：把终止符改为**必需** —— `/^\s*'[^']*。'\s*[+,]$/`。
**验证方式也改对了**：不再猜，而是**把那一行 dump 出来逐字符看**，并**单独跑一次正则**确认。

**教训（本会话第 3 次同源）**：**正则式判据必须先对着真实样本验证一次** ——
第 67 轮是"审计脚本必须先自证覆盖范围"，第 83 轮是"patch 逐行 dump 才看出 `- id:`"，本轮是这一条。
**三次都是同一个毛病：先写判据，再看数据。**
